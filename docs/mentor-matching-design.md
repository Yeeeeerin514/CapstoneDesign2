# 안심알바 — 멘토·멘티 매칭 시스템 설계서

> 작성일: 2026-05-17
> 목적: 팀원 전체가 매칭 시스템의 구조와 정당성을 이해하고, 백엔드/프론트/AI 파트가 어디서 무엇을 맡을지 합의하기 위함.

---

## 0. 한 줄 요약

> **임금체불 피해 해결 경험자(멘토)** 와 **현재 피해 중인 사용자(멘티)** 를, 정형 프로필 데이터만으로 매칭하는 4-Layer 시스템.
> `Gower 유사도 → Gale-Shapley 안정매칭 → Thompson Sampling 가중치 학습 → SHAP 설명`

---

## 1. 왜 만드는가 (Motivation)

### 1.1 현재 안심알바가 풀고 있는 것
- 임금체불 **예방** (공고 분석, 계약서 분석, 출퇴근 기록)
- 임금체불 **계산·신고서 작성** (진정서 LLM 초안)

### 1.2 현재 빠진 것
- 실제 신고/소송 과정에서 **사람이 사람에게 묻고 싶은 영역**이 비어 있음
  - "노동청 진정 가면 진짜 어떻게 진행돼요?"
  - "5인 미만 사업장이면 주휴수당 못 받는다는데 사례 좀…"
  - "사장이 잠적했는데 어떻게 추적했어요?"
- LLM은 일반론밖에 못 줌. **경험자의 구체 케이스**가 가장 강력함.

### 1.3 매칭 시스템의 가치
1. **사용자 가치**: 가장 비슷한 케이스를 해결한 멘토와 연결 → 실질적 도움
2. **데이터 가치**: 매칭 결과/피드백이 쌓이면서 안심알바만의 케이스 DB 형성
3. **기술 가치**: 캡스톤 평가 측면에서 알고리즘적 난이도 확보 (교수님 피드백 대응)

## 2. 핵심 개념과 용어

| 용어 | 정의 |
|------|------|
| **멘토 (Mentor)** | 과거 임금체불 피해를 **해결 완료**한 사용자. 자발적으로 멘토 등록한 사람. |
| **멘티 (Mentee)** | 현재 임금체불 피해를 겪고 있거나 신고 진행 중인 사용자. |
| **매칭 (Matching)** | 멘티 한 명에게 적합한 멘토 1~3명을 자동으로 짝지어주는 행위. |
| **프로필 벡터** | 멘토/멘티의 특성을 정형 데이터로 표현한 벡터. |
| **캐파 (Capacity)** | 한 멘토가 동시에 담당 가능한 멘티 수 (기본 3명). |

> **이번 설계에서 빠진 것**: 사연 자유서술 텍스트 임베딩(NLP)은 1차 버전에서 제외. **모든 매칭은 카테고리형 프로필 데이터만으로 수행한다.**

## 5. 4-Layer 알고리즘 상세

### Layer 1 — 후보 필터링 (Hard Filter)

**규칙**: 다음 조건을 만족하는 멘토만 후보군에 진입.

- `active = true`
- 현재 진행중 매칭 수 < `capacity`
- `damage_types` 교집합 ≥ 1개 (피해유형 1개도 안 겹치면 무의미)

→ 1만 명 멘토가 있어도 후보는 보통 수십~수백 명으로 줄어듦. 이후 계산 비용 ↓.

---

### Layer 2 — Gower 거리 기반 유사도 계산

#### 왜 Gower인가?
- 우리 데이터는 **카테고리(업종) + 다중선택(피해유형) + 서수형(금액구간) + 불리언(외국인)** 이 섞여 있음
- 일반 유클리드/코사인은 카테고리에 부적합
- Gower 거리는 **혼합형 데이터에 표준적으로 쓰이는 거리 함수** (Gower, 1971)

#### 특성별 거리함수

| 특성 | 타입 | 거리함수 |
|------|------|----------|
| 피해유형 | 다중선택 | `1 - Jaccard(A, B)` |
| 업종 | 카테고리 | `0 if 같음 else 1` |
| 고용형태 | 카테고리 | `0 if 같음 else 1` |
| 사업장규모 | 서수 | `|순위차| / 2` (UNDER_5↔OVER_30이면 1.0) |
| 금액구간 | 서수 | `|순위차| / 4` |
| 지역 | 카테고리(계층) | 같은시도=0 / 인접시도=0.5 / 그외=1 |
| 연령대 | 서수 | `|순위차| / 4` |
| 외국인여부 | 불리언 | `0 if 같음 else 1` |

#### 최종 거리

```
distance(M, T) = Σᵢ wᵢ · dᵢ(M, T)    where Σwᵢ = 1
```

- 초기 가중치(휴리스틱):

| 특성 | 초기 wᵢ | 근거 |
|------|---------|------|
| 피해유형 | **0.30** | 경험 영역이 같아야 도움이 됨 |
| 사업장규모 | **0.20** | 5인 미만/이상은 근로기준법 적용 자체가 달라짐 |
| 해결방법(*) | 0.15 | 멘티가 원하는 해결경로 기준 |
| 업종 | 0.10 | 업계 관행 |
| 지역 | 0.10 | 관할 노동지청 동일 시 유리 |
| 고용형태 | 0.05 | |
| 금액구간 | 0.05 | |
| 인구통계 | 0.05 | 연령/외국인 |

(*) 해결방법은 멘토에게만 있는 항목 → "멘티가 선호하는 해결방법"을 입력받아 멘토의 `resolution_methods` 포함 여부로 0/1 거리.

---

### Layer 3 — Gale-Shapley 안정 매칭

#### 왜 단순 top-K 추천이 아니라 안정매칭인가?
- top-K 추천은 **인기 멘토에게 멘티 쏠림** 발생 → 멘토 번아웃, 매칭 실패
- Gale-Shapley는 **양방향 선호도 + 캐파 제약** 하에서 **"서로 깨고 싶지 않은" 안정 상태**를 보장
- 알고리즘이 종료 보장(O(n²)) + 노벨 경제학상(2012, Shapley·Roth) 정당성

#### 절차

1. **멘티 선호 리스트**: 거리 작은 멘토 top-10 정렬
2. **멘토 선호 리스트**: 자기와 거리 작은 멘티 정렬 (역대칭 거리 사용)
3. **반복**:
   - 매칭 안 된 멘티가 가장 선호하는 멘토에게 청혼(propose)
   - 멘토는 자기 캐파 내에서 가장 선호하는 멘티들만 임시 수락
   - 모든 멘티가 매칭되거나 청혼 리스트 소진 시 종료

#### 출력
- 멘티당 1~3명의 멘토 (`rank` 1~3)
- 멘토당 최대 `capacity`명의 멘티

---

### Layer 4 — Thompson Sampling으로 가중치 학습

#### 콜드스타트 문제
- 서비스 초기엔 피드백 데이터 = 0
- 휴리스틱 가중치 w₁~w₈이 정말 옳은지 알 수 없음
- 그렇다고 데이터 모으는 동안 가만히 있을 수도 없음

#### Thompson Sampling이 푸는 것

각 가중치 `wᵢ`를 **Beta(αᵢ, βᵢ) 분포**로 모델링:
- 초기값: `Beta(1, 1)` = 균일분포 (무지 상태)
- 매칭 결과 피드백:
  - `resolved = true` 또는 `helpfulness ≥ 4` → 매칭에 영향이 컸던 특성 i의 `αᵢ += 1`
  - `resolved = false` 또는 `helpfulness ≤ 2` → `βᵢ += 1`
- 매칭할 때마다 각 분포에서 샘플링 → 정규화 → 그 매칭의 가중치로 사용

#### 효과
- 피드백 10~20건만 있어도 가중치가 의미있게 움직임
- "탐색(다양한 가중치 시도) ↔ 활용(좋다고 판단된 가중치 사용)" 자동 균형
- 데이터가 쌓이면 분산 작아지며 안정화 → 수백 건 이후엔 사실상 점추정과 같음

#### 어떤 특성이 매칭에 "기여"했는지 어떻게 판단?
→ Layer 5의 Explanation과 같은 메커니즘 (특성별 거리 기여도 = `wᵢ · dᵢ`).
기여도 큰 상위 3개 특성에 대해 α/β 업데이트.

---

### Layer 5 — 설명 가능성 (Explanation)

매칭 결과를 멘티에게 보여줄 때, 단순 "추천 멘토"가 아니라 **이유 카드**로 제공.

#### 산출 방식
각 특성 i의 **유사도 기여도** = `wᵢ · (1 - dᵢ)` 를 계산 → 내림차순 상위 3개를 한국어 문장으로 변환.

#### 예시 출력
```json
{
  "explanation": [
    {"feature": "damage_types", "score": 0.27, "label": "같은 피해유형 (주휴수당·임금체불)"},
    {"feature": "workplace_size", "score": 0.20, "label": "같은 사업장 규모 (5인 미만)"},
    {"feature": "resolution_methods", "score": 0.12, "label": "원하시는 해결방법(노동청 진정) 경험 있음"}
  ]
}
```

→ 멘티 UI에 "이 멘토를 추천한 이유" 칩 3개로 표시.

#### 데이터가 쌓이면 (Phase 2)
- 매칭 성공/실패를 라벨로 한 LightGBM 모델 학습
- **SHAP** 값으로 특성 기여도 산출 → 더 정교한 설명
- 1차 버전에선 위의 단순 기여도로 충분

## 6. API 설계 (기존 백엔드에 추가)

### 멘토 (`/api/mentors`) 인증 필요
- `POST /api/mentors` — 멘토 등록 (멘토 프로필 생성)
- `GET /api/mentors/me` — 내 멘토 프로필 조회
- `PUT /api/mentors/me` — 멘토 프로필 수정
- `PUT /api/mentors/me/active` — 활동/휴식 토글

### 매칭 (`/api/matchings`) 인증 필요
- `POST /api/matchings/request` — 멘티 매칭 요청 (`mentee_request` 생성 + 매칭 실행)
  - 입력: 신고 ID(`analysis_log`) 또는 직접 프로필
  - 출력: 추천 멘토 1~3명 + 각자의 explanation
- `GET /api/matchings/me` — 내가 받은/제안한 매칭 목록
- `POST /api/matchings/{id}/accept` — 멘토가 수락
- `POST /api/matchings/{id}/reject` — 멘토가 거절 → 다음 후보로 재매칭
- `POST /api/matchings/{id}/feedback` — 멘티 피드백 제출 → Thompson 업데이트 트리거

### 채팅 (`/api/chat`) ※ 별도 트랙
- 1:1 채팅 (FCM + WebSocket 또는 폴링)
- 본 설계서 범위 외 (Phase 1.5로 분리)

## 9. 교수님 설득 포인트 (캡스톤 평가용)

1. **혼합형 데이터에 적합한 Gower 거리**를 채택 — 임의로 코사인 쓰지 않고 데이터 특성에 맞는 거리함수 선택의 정당성.
2. **Gale-Shapley 안정매칭** — 노벨상 알고리즘을 도메인(임금체불 멘토링)에 적용. 캐파 제약 + 양방향 선호 처리.
3. **Thompson Sampling 베이지안 온라인 학습** — "데이터가 없다"는 콜드스타트 문제를 정면 돌파. 일반적인 캡스톤이 안 다루는 깊이.
4. **Explanation by Contribution** — 단순 블랙박스 추천이 아닌 설명가능 추천. 추후 SHAP 확장 로드맵까지 제시.
5. **점진적 고도화 아키텍처** — 데이터가 쌓이면 LTR/GNN으로 자연스럽게 진화 가능한 4-Layer 구조.
